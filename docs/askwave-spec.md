# Askwave – Chat with your docs

A small FastAPI project to practice FastAPI, LLMs and RAG. A user creates **projects**, uploads documents into each one, and chats with those documents. Every project is fully isolated: questions in one project only use that project's documents.

Good example use case for Xperlean (supply chain / Industry 4.0): a project per supplier or per machine, filled with technical manuals, contracts or procedures.

## Core idea

- A **Project** groups documents and conversations.
- A user can create several projects, each with its own set of documents.
- Inside a project, the user can:
  - upload one or many documents (PDF, Markdown, TXT),
  - add new documents later,
  - delete a document (its knowledge disappears from the answers),
  - ask questions and keep chatting over time.
- Answers are generated by an LLM using only the relevant parts of the project's documents, and always come **with sources** (document name + page).

## Main concepts

| Entity | Description |
|---|---|
| Project | A container with a name and description. Owns documents and conversations. |
| Document | An uploaded file inside a project. Has a processing status. |
| Chunk | A small piece of text from a document, with its embedding vector. |
| Conversation | A chat thread inside a project. |
| Message | One question or answer in a conversation, with the sources used. |

## User flows

1. **Create a project** → name + description.
2. **Upload documents** → the API saves the file, creates a document with status `pending`, and starts processing in the background.
3. **Processing** → the document moves to `processing`, then `ready` (or `failed` with an error message).
4. **Ask a question** → only `ready` documents of this project are searched. The answer streams back word by word, with sources.
5. **Continue later** → the user reopens the project, adds or deletes documents, and keeps chatting in the same or a new conversation.
6. **Delete a document** → the file and all its chunks are removed, so future answers no longer use it.
7. **Delete a project** → removes all its documents, chunks and conversations.

## Architecture

```
Client
  │
  ▼
FastAPI
  ├── Upload ──► file storage (local folder, later S3)
  │              └── BackgroundTask: extract → chunk → embed → store
  ├── Ask ─────► embed question → vector search (filtered by project_id)
  │              → build prompt with top chunks + chat history
  │              → LLM → stream answer (SSE) + sources
  └── CRUD ────► PostgreSQL + pgvector
```

## Tech stack

- **FastAPI** with async endpoints
- **Pydantic** models for every request and response
- **PostgreSQL + pgvector** for data and vector search
- **SQLModel** or SQLAlchemy for the ORM
- **LLM provider** (OpenAI, Anthropic or Gemini) for answers
- **Embedding model** (provider API or a local sentence-transformers model)
- **pypdf** for PDF text extraction
- **Docker Compose** for the API and the database

## Data model

**projects**
- id (UUID), name, description, created_at

**documents**
- id (UUID), project_id (FK), filename, mime_type, size, storage_path
- status: `pending` | `processing` | `ready` | `failed`
- error_message, page_count, created_at

**chunks**
- id (UUID), document_id (FK), project_id (FK, for fast filtering)
- content (text), page_number, chunk_index
- embedding (vector)

**conversations**
- id (UUID), project_id (FK), title, created_at

**messages**
- id (UUID), conversation_id (FK)
- role: `user` | `assistant`
- content, sources (JSON: document id, filename, page), created_at

Deleting a document or project cascades to its chunks (and to conversations for a project).

## API endpoints

**Projects**
- `POST /projects` – create a project
- `GET /projects` – list projects
- `GET /projects/{project_id}` – project details with document count
- `PATCH /projects/{project_id}` – rename or update description
- `DELETE /projects/{project_id}` – delete a project and everything inside

**Documents**
- `POST /projects/{project_id}/documents` – upload one or several files
- `GET /projects/{project_id}/documents` – list documents with status
- `GET /projects/{project_id}/documents/{document_id}` – document details
- `DELETE /projects/{project_id}/documents/{document_id}` – delete file and chunks

**Chat**
- `POST /projects/{project_id}/conversations` – start a conversation
- `GET /projects/{project_id}/conversations` – list conversations
- `GET /conversations/{conversation_id}/messages` – message history
- `POST /conversations/{conversation_id}/ask` – ask a question, streamed answer (SSE)

## Ingestion pipeline

Runs as a FastAPI **BackgroundTask** after upload:

1. Set document status to `processing`.
2. Extract text page by page (keep the page number).
3. Split into chunks of about 500–800 tokens with a small overlap.
4. Create embeddings for each chunk (batched).
5. Insert chunks with `project_id` and `document_id`.
6. Set status to `ready`, or `failed` with the error message.

Limits: max file size, allowed types (PDF, MD, TXT), max documents per project.

## Question answering (RAG)

1. Save the user's question as a message.
2. Embed the question.
3. Vector search in `chunks` **where project_id = current project**, top 5.
4. Build the prompt: system instructions + retrieved chunks + last few messages of the conversation + the question.
5. Instruct the LLM to answer only from the given context and say when it doesn't know.
6. Stream the answer to the client with **server-sent events**.
7. Save the final answer with its sources.

## Key design points to talk about

- **Isolation between projects**: every vector search is filtered by `project_id`, so documents never leak between projects.
- **Async processing**: uploads return immediately; heavy work runs in the background with clear statuses.
- **Cited answers**: each answer lists the documents and pages it used, which builds trust.
- **Streaming**: answers appear word by word for a better experience.
- **Dependency injection**: database session, settings and LLM client injected with `Depends`, easy to swap providers.
- **Clean deletion**: deleting a document removes its chunks, so the knowledge base always matches what the user sees.
